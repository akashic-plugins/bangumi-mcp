# 收藏完整与大量查询确认边界

- 状态：`Accepted`
- 目标版本：`0.4.0`
- 日期：2026-08-04
- 官方依据：[Bangumi API](https://bangumi.github.io/api/) 与 [OpenAPI 定义](https://bangumi.github.io/api/dist.json)
- 前置设计：[用户收藏列表设计](collection-list.md) 与 [收藏查询意图与展示边界](collection-query-intent.md)

## 1. 决策

以下任一条件成立时，插件必须在读取收藏明细前展示查询预览，并等待用户在下一条消息中明确确认：

1. 查询计划需要读取候选集的全部收藏。
2. 单个逻辑查询计划预计读取达到或超过 100 条收藏明细。
3. 同一查询会话通过连续分页累计将读取达到或超过 100 条唯一收藏明细。

该规则与用户如何措辞无关。即使用户已经说“全部”、“所有”或“完整”，仍必须先展示范围、数量和代价，再等待一次确认。

确认阈值是风险告知边界，不是查询上限。用户确认后，插件可按计划读取 100 条以上或完整候选集，不得在 100 或 200 条处静默截断。

## 2. 术语与阈值

### 2.1 完整查询

完整查询是为了声称“全部”、计算完整统计、执行 Bangumi 不支持的派生筛选，或以其他方式得出覆盖整个候选集的结论，而必须遍历所有候选收藏的查询。

例如：

- 全部列出搁置动画。
- 找出所有评分不低于 8 分的作品。
- 计算所有收藏的平均评分。
- 按插件本地规则筛选 Bangumi 接口不支持的字段。

即使候选集只有 24 条，完整查询也必须确认。

### 2.2 大量查询

大量查询是预计或累计读取达到或超过 100 条唯一收藏明细的查询。

- 累计读取最多 90 条时不触发数量阈值。
- 下一个 10 条展示页将使累计数达到 100 时，必须在读取第 91 至 100 条前确认。
- 多次调用普通分页工具不得绕过阈值；同一过滤条件和排序下的连续分页属于同一查询会话。
- 返回条目达到 100 或内部扫描条目达到 100，任一条件成立都必须确认。

### 2.3 不触发的操作

以下操作本身不需要大量查询确认：

- `count_collections` 使用 `limit=1` 只读取总数元数据，即使 `total` 大于 100。
- 普通 `list_collections` 只读取当前 10 条，且同一查询会话累计少于 100 条。
- 查询单个已知 `subject_id` 的收藏和观看进度。
- 从已经确认并完成的短期内存结果中翻页、排序或进一步筛选，不产生新的 Bangumi 完整读取。

## 3. 确认流程

### 3.1 预览

在完整或大量读取前，插件只能使用已有查询会话中可信的 `total`；如果尚无可信总数，才允许执行一次 `limit=1` 的轻量计数探测。预览阶段不得预取其他收藏明细。预览必须显示：

- 目标账户是当前 Token 用户，不回显 Token。
- Bangumi 服务端过滤：作品类型和收藏状态。
- 插件本地过滤或分析条件，例如 `rating >= 8`。
- 候选收藏总数。
- 预计读取的明细条数。
- 预计 Bangumi 列表请求数：确认后的完整扫描和超阈值继续读取都按每页 50 条计算。
- 触发确认的原因：完整查询、达到 100 条，或两者均成立。
- 该操作只读，不会修改 Bangumi 收藏。
- 单次使用的 `confirmation_text` 和过期时间。

预览完成后必须结束当前轮，不得在同一轮执行查询。

### 3.2 确认

用户下一条消息只有在去除首尾空白后与 `confirmation_text` 逐字一致，才授权执行该查询计划。模糊同意、更改条件、旧确认或长期授权均不生效。

一次有效确认覆盖：

- 该计划的全部 Bangumi 分页读取。
- 已声明的本地筛选、统计或排序。
- 从同一内存结果中继续展示后续页。
- 同一范围内可恢复的只读网络重试。

不得对同一计划的第 2、第 3 或后续 Bangumi 分页重复询问。

### 3.3 需要新确认的情况

仅当以下条件之一成立时，才需要重新预览和确认：

- 作品类型、收藏状态、本地筛选、分析目标或输出模式发生实质变化。
- 确认在执行前过期。
- MCP 进程重启或短期结果已失效，后续操作必须产生新的完整或超阈值读取。

仅调整已确认结果的展示页、字段顺序或排序方式，且不需要新的 Bangumi 读取时，不得重复询问。

## 4. MCP 工具边界

### 4.1 无需确认的工具

- `count_collections`：使用 `limit=1` 获得候选总数。
- `list_collections`：创建普通查询会话并固定读取首页 10 条，返回不透明 `query_id`；不再向模型暴露裸 `offset`。
- `continue_collection_query`：只接受 `query_id`，使用会话内服务端保存的下一偏移量读取 10 条。当下一页将使累计读取达到或超过 100 条时，工具必须在发起 Bangumi 请求前改为返回确认预览。
- `get_collection_status`：查询单一已知条目。

```python
list_collections(
    subject_type: SubjectTypeFilter = "all",
    status: CollectionStatusFilter = "all",
) -> str

continue_collection_query(query_id: str) -> str
```

`query_id` 必须是随机、不可猜测、带 TTL 的服务端能力标识，并绑定当前 Token 用户、过滤条件、下一偏移量和累计已读唯一条目数。过期、伪造或已完成的 `query_id` 必须 fail-loud。

### 4.2 需要确认的工具

`list_all_collections` 不得继续作为可直接执行的公开工具。完整和大量查询改为两阶段工具：

```python
prepare_collection_query(
    subject_type: SubjectTypeFilter = "all",
    status: CollectionStatusFilter = "all",
    operation: Literal["list_all", "filter", "analyze"],
    min_rating: int | None = None,
    max_rating: int | None = None,
    requested_count: int = 10,
    return_all_matches: bool = False,
) -> str
```

`prepare_collection_query` 只允许执行 `limit=1` 计数探测，生成不可修改的查询计划、`confirmation_id` 和 `confirmation_text`。

```python
execute_prepared_collection_query(
    confirmation_id: str,
    confirmation_text: str,
) -> str
```

`execute_prepared_collection_query` 只能执行预览中的固定计划，不接受新的过滤或数量参数。它每页向 Bangumi 请求 50 条，在插件内部完成派生筛选与统计。

### 4.3 查询会话与短期结果

插件维护有界、带过期时间的内存查询会话，用于：

- 统计同一普通分页查询已读取的唯一条目数。
- 阻止多次 10 条分页绕过 100 条确认阈值。
- 保存已确认查询的规范化结果，供后续展示或二次筛选复用。

普通分页会话累计读取 90 条后，下一次 `continue_collection_query` 必须只生成一个“允许该会话继续读取至远端 `total`”的确认计划，不得读取第 91 至 100 条。用户确认后，后续 Bangumi 请求每次最多读取 50 条并放入该会话的短期内存结果；仍然只在用户每次明确要求“继续”时展示下一个 10 条结果页，但从内存结果翻页不发起新的 Bangumi 请求，同一 `query_id` 也不再重复询问。

该状态不写入 plugin-data，不持久化 Access Token，不在日志中输出收藏明细。MCP 进程重启后状态丢失是预期行为。

## 5. 执行与结果语义

- 确认前的普通展示查询固定使用 `limit=10`，不预取尚未授权的明细。确认后的完整或超阈值 Bangumi 列表请求固定使用 `limit=50`，减少 API 往返。
- 完整查询必须读取到 `returned == total`；不得以前 100 或前 200 条伪装成完整结果。
- 跨页 `total` 发生变化、出现重复 `subject_id` 或提前空页时 fail-loud，不伪造时间点一致的快照。
- 评分等 Bangumi 不支持的条件必须在插件服务层进行结构化筛选，不得让模型通过 10 条一页的工具调用手工汇总。
- 普通“列出”默认展示最多 10 个匹配结果；后续“继续”从已确认的内存结果读取。
- 用户要求“全部列出”时，确认后必须保留全部匹配结果语义，不得在查询层静默截断。如果宿主输出存在独立技术上限，必须在预览中说明，不得在确认后才隐式降级。

## 6. 示例

### 6.1 普通列表

用户：“列出我搁置的动画。”

行为：读取前 10 条，说明总数和是否还有下一页，不需要确认。

### 6.2 明确全部查询

用户：“全部列出我搁置的 24 部动画。”

行为：先用 `limit=1` 确定候选总数，展示“将完整读取 24 条，预计 1 次列表请求”并等待确认。即使数量小于 100，因为是完整查询，仍必须确认。

### 6.3 派生评分筛选

用户：“列出我打 8 分以上的作品。”

行为：Bangumi 不支持服务端评分过滤。先用 `limit=1` 取得候选收藏总数。若为 250 条，展示“将扫描全部 250 条，预计 5 次列表请求，并在本地筛选 `rating >= 8`”，然后等待确认。确认后每页读取 50 条，不得读取 25 个 10 条分页。

### 6.4 普通分页越过阈值

用户已通过普通“继续”分页读取 90 条，再次请求下一页。

行为：在读取第 91 至 100 条前展示累计范围、剩余总数和按每批 50 条计算的预计请求数，并等待一次确认。确认后，插件可每次预取 50 条到内存，但每次“继续”仍只展示 10 条；后续翻页不再重复询问。

### 6.5 只查数量

用户：“我有多少部动画收藏？”

行为：使用 `limit=1` 读取 `total`。即使结果是 1000，也没有读取 1000 条明细，因此不需要确认。

## 7. 安全与隐私

- 该确认仅授权只读查询，不能被复用为 Bangumi 写入确认。
- 完整与大量查询确认存储必须与写入确认分开，但可复用相同的单次、过期和原子消费机制。
- Access Token 仍只存在 `config.local.toml`，不出现在预览、确认文本、日志或工具结果中。
- 短期查询结果只存于 MCP 进程内存，带有 TTL 和容量上限，不写入 Git 或 plugin-data。
- 日志只记录查询计划 ID、数量、请求数和错误分类，不记录收藏标题、评论、标签或原始响应。

## 8. 失败与变更

- 用户在确认时修改范围或条件，旧计划作废，生成新预览。
- 查询执行期间发生可判定的暂时读取错误时，在原确认范围和 TTL 内可做有界重试，不重复询问。
- 远端收藏总数或分页内容在执行期间变化时，不自动重新完整扫描；报告结果不能被证明完整。用户后续要求重试时，因为将产生新的完整查询，需要新预览与确认。
- 不得因为查询是只读就降级成无确认操作。

## 9. 测试与验收

1. 完整读取 24 条也必须先预览，且 prepare 阶段只发起一次 `limit=1` 请求。
2. 读取前 90 条且不声称完整时不因数量规则触发确认；使累计数达到 100 的下一页读取前必须确认。
3. 连续调用 10 次 10 条分页不能绕过达到 100 条时的确认边界。
4. 普通分页不向模型暴露裸 `offset`；伪造、过期或跨过滤复用 `query_id` 都会在 Bangumi 请求前失败。
5. 只询总数时始终使用 `limit=1`，不因 `total > 100` 触发确认。
6. 评分不低于 8 分的查询在执行前显示全量扫描预览；确认后以 50 条为一页扫描，不使用 10 条展示页执行分析。
7. 用户明确说“全部”不会跳过预览与下一轮确认。
8. prepare 和 execute 不得在同一轮调用。
9. 一次确认覆盖同一计划的全部分页，不在每 50 条、每个结果页或每次只读重试时重复确认。
10. 确认计划不能执行不同的过滤、分析目标或数量范围。
11. 全部测试使用假 HTTP 会话，不使用真实 Bangumi Token 或账户。

## 10. 实现顺序

1. 实现查询计划、确认存储和短期查询会话，与写入确认分离。
2. 将直接完整读取工具替换为 prepare/execute 两阶段工具。
3. 在服务层实现每页 50 条的完整扫描和评分筛选。
4. 为普通分页引入查询会话计数，阻止达到 100 条时的无确认读取。
5. 更新 Skill，确保任何“全部”措辞也必须先预览，确认后不重复询问。
6. 补充 MCP schema、Service、确认、分页累计、缓存和敏感信息边界测试。
7. 通过 Plugin API v2 合同和 Akashic 已提交快照安装 smoke 后，再将插件版本提升为 `0.4.0`。
